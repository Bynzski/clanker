# Agent attention: lifecycle integration

Research and implementation notes for [issue #38](https://github.com/Bynzski/clanker/issues/38), checked 2026-09-24. The installed CLIs inspected locally were Codex 0.156.1, Claude Code 2.1.195, OpenCode 1.18.32, and Pi 0.85.1. The hook mappings below come from vendor documentation and installed CLI help/types. Clanker now implements the local observer, attention state, pane naming, and navigation described below; live hook delivery still needs manual verification on Linux and Windows.

## What Clanker currently knows

- `SPAWN_TERMINAL` chooses a harness from the workspace selection. `SESSION_INVOKE` has a separate resume path. Both call `spawnPtyProcess` and now register launch-scoped observers when enabled.
- Renderer `Terminal` stores the actual harness launched and a human display name alongside `id`, `pid`, and `workingDir`. `WorkspaceTab.harness` is a default for future panes and can change after existing panes start. The terminal ID maps to a pane within a workspace; a harness session ID alone does not.
- `terminalSessionBridge` receives PTY data, process exits, and agent attention updates globally, including parked workspaces. The pane header now displays its human name and supported lifecycle state; workspace tabs display a workspace name and attention count. A PTY exit is a process event, not an agent-turn event. On POSIX, the wrapper starts a shell after the harness exits; on Windows, the harness is spawned via `cmd.exe /c`.
- Layout persistence stores pane positions/count, not live PTY identity. Attention is runtime state and should be discarded on app restart or terminal disposal.

## Extension contract

Clanker uses an **opt-in, process-local observer** per launched harness. The launch adapter module is keyed by harness ID and keeps each harness's install method and event mapping separate from the shared broker. A disabled adapter leaves the status label hidden. An enabled adapter without a verified event reports `unknown`, not `complete` or `idle` inferred from PTY output. A future adapter can add capability metadata and minimum tested versions when those are verified across platforms.

Each observer sends only an allowlisted event, for example `turn_started`, `input_requested`, `input_resolved`, `turn_completed`, or `session_ended`. An event contains a schema version, a launch-scoped nonce, and an optional opaque harness session/turn ID for deduplication. It must not include prompts, tool arguments, transcript paths, commands, messages, or credentials. The main process assigns `terminalId` at spawn and owns the nonce. Main authenticates the event and forwards the terminal ID; the renderer resolves that ID to its owning workspace and pane from the workspace store. The workspace does not exist yet when its first PTYs spawn, so main cannot derive it at spawn time. Never accept a workspace ID or terminal ID claimed by a hook payload.

The implementation uses one `node:net` listener bound to `127.0.0.1` on an ephemeral port on Linux and Windows. It passes port plus a separate random token in the environment of **that PTY spawn only**. Main limits message size, accepts only allowlisted fields/events, validates the token, harness, and optional ID formats, then forwards a minimal attention event over preload. Session IDs may change inside a PTY; the launch token is what binds an event to its pane. The broker unregisters on terminal kill, natural exit, workspace cleanup, and app shutdown. A late event from a prior launch cannot update a new pane. The token protects against accidental cross-pane events; it is an advisory UI channel, not a security permission boundary.

New launches and history resumes both register through their callers and release through `spawnPtyProcess` exit. The adapter code is separate from `ptySpawn`. Users opt in per harness under Settings → Harness Defaults → Agent attention. Clanker adds Pi's explicit `--extension`, Claude's additional `--settings`, Codex's per-launch `notify` override only when no existing notifier/profile is detected, and an OpenCode plugin through `OPENCODE_CONFIG_DIR` only when the user has no custom directory and `--pure` is absent. If an additive path is unavailable, that pane stays `unknown`.

## State and names

Store actual `harnessId | null` on each renderer terminal. The main broker's random token identifies its live launch. Do not infer a pane's harness from the mutable workspace default, process name, or the title of a resumed chat.

Separate **lifecycle** (`unknown`, `running`, `needs_input`, `turn_complete`) from **attention** (`unseen` boolean and time). A visited pane clears `unseen` only; it does not claim that an unanswered prompt was resolved. A verified new turn or input resolution changes lifecycle. A background `needs_input` or `turn_complete` sets `unseen`; foreground events update status without a badge. On unexpected process exit, clear live status to `unknown` or a distinct process-exited label, never synthesize turn completion. Keep state in an app-level store so cold workspaces receive updates.

Default pane labels are human names from a Grateful Dead inspired pool: `Samson`, `Delilah`, `Jerry`, `Bobby`, and others. Names are unique within a workspace while panes are open; after the pool is exhausted they get a numeric suffix. The label is separate from identity and status. Workspace tabs keep their existing user-controlled names. A status label appears next to the pane name, and an aggregate badge appears on its workspace tab: input needed first, then completed. Multiple events in one workspace aggregate as counts.

`Next needing input` should select the next unseen `needs_input` terminal in stable workspace-tab and pane-layout order, wrapping from the current pane. If none exists, it can select unseen completed turns. Selection must activate the owning workspace, reveal/focus the exact pane, and acknowledge only that pane. Never clear another terminal's state because the workspace tab was opened.

## Build sequence and evidence gate

1. Implemented: main-process broker and validation, per-harness launch adapters, opt-in settings, terminal metadata, state reducer, human pane names, indicators, aggregation, and jump navigation. Focused tests cover token isolation, hook transport, names, state transitions, and navigation.
2. Still to verify manually: run controlled lifecycle traces on Linux and Windows for each installed harness. Record event payload shapes, ordering, resume behavior, user config coexistence, failures, and whether permission/question prompts are actually observable. Use synthetic prompts that contain no secrets.
3. Version capability diagnostics remain a possible follow-up. Unsupported events on enabled integrations show `unknown`; disabled integrations show no status label. Clanker does not infer turns from PTY output.

The main remaining verification questions are whether Claude `Stop` can report completion before another hook continues, whether OpenCode's custom plugin directory merges with all existing global/project plugins on supported versions, and whether each harness exposes an actual-waiting event for questions beyond permission prompts. Codex has no verified external approval notification here. Clanker shows `unknown` rather than inventing unsupported states.
